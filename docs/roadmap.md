# RM-validation: earn the next prototype stage

The first prototype implements offline import, provenance, local persistence,
reread candidates, and descriptive associations. It does not establish the
effectiveness of project-memory optimization. [§GOAL-utility](goals.md#goal-utility-useful-decisions-before-a-larger-service)

## 1. Capture fidelity

Add a runtime boundary adapter that can observe final model request payloads,
then compare captured spans against controlled fixtures. Audit auto-loaded
instructions, search output, shell transformations, branching, subagents, and
compaction before claiming comprehensive context coverage. Add JSON Schema once
the first wire format has survived real use.

## 2. Ground and accounting joins

Join Grund's versioned declaration/section map to returned ranges. Import Rhei
invocation accounting as a separate measured dataset. Preserve uncached input,
cache reads/writes, output, and measurement coverage. Resolve historical identity
using the recorded revision, never the live checkout.

## 3. Utility experiment

Collect representative tasks across foundation repositories. Use time-separated
training and evaluation tasks, frozen revisions/models, matched budgets, and
repeated executions. Compare profile-guided section discovery or memory changes
with the existing workflow and simple citation/lexical/co-change baselines.
Measure executable task success, provider usage/cost, latency, and capture cost.
A provisional target is a repeatable 15% cost reduction without meaningful
quality loss; a small pilot alone cannot establish noninferiority. Include
required project conventions even if infrequently observed.

## 4. Separate service decision

Add another runtime and consumers only when useful decisions recur. Live capture,
background services, automatic context bundles, outcome-conditioned inference,
and source-memory rewrites remain outside this prototype.
